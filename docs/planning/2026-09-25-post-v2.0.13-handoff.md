## Ordered checkpoints

### 1. Establish a current recovery point

From the NAS side, identify the latest backup of each of the six persisted SQLite
databases. If there is no sufficiently current, consistent set, make one with the
configured maintenance backup path or SQLite's
[online backup API](https://www.sqlite.org/backup.html). Verify database integrity
and a restorable disposable copy; retain the source time, database names,
integrity results and hashes in a manifest. Keep a protected off-NAS copy. This is
the prerequisite for a safe future deployment or rollback. Do not overwrite current
databases with the 00:40 copy: later trades and approval state would need explicit
reconciliation first.

**Done when:** the operator can identify a verified current backup set and its
off-NAS copy, and has a recovery path that preserves post-backup effects.

### 2. Reconcile the two SOL fills

Run the NAS-local, reader-key, read-only
[`tools/reconcile_trade_history.py`](../../tools/reconcile_trade_history.py) for
`--symbols SOL` against the persisted `live.db`. Inspect trade IDs, any
`missing_locally` versus `deferred` rows, non-trade ledger movements and the
quantity comparison. The tool's docstring contains the reviewed backfill runbook.
If a real gap appears, stop for that runbook's dry-run and post-state checks; a
reported gap is not authority for an ad hoc database edit.

**Done when:** the two executions are accounted for locally, or a precise gap is
recorded with its reviewed recovery action and verification.

### 3. Observe production for a bounded window

Read back the selected image/revision, all service health, relevant error logs,
daily reconciliation, and operator approval/Harvester command state. Treat an
unexercised withdrawal path as an explicit evidence limit. For formal 2.0.x
acceptance, use the [closeout plan's](2.0-closeout-and-2.1-entry-plan.md)
preselected finite observation window and record missing event-dependent evidence
as a limitation rather than a pass. No diagnostic transfer is implied by this
handoff.

**Done when:** the observation has a dated receipt, anomalies have dispositions,
and the remaining limitations are clear to the operator.

### 4. Decide and prepare the separate maintenance patch

After the data checks, decide whether to package merged PR #158 as the next patch.
Freeze the exact candidate, confirm that the completed independent review covers
its integrated diff under the pre-deploy rule, run the release gates, and verify
the tag-built image digest. For a deployment,
prepare the exact Portainer file-stack change and verify the persisted tag, digest,
container revision and health after redeploy. A passing `main` build is not a tag
release or a production deployment. Follow the
[release and rollback gates](2.0-closeout-and-2.1-entry-plan.md#7-release-acceptance-and-rollback).

**Done when:** the patch is either explicitly deferred, or has its own verified
release, deployment and rollback receipts. Keep it separate from formal 2.0.x
acceptance.

### 5. Make the formal closeout decision, then plan N0

Compare the evidence above and the
[known limitations](../release/v2.0-known-limitations.md) with the closeout plan's
formal-close criteria. Record each accepted exception, the operator decision and
date in the roadmap. Open N0 only after that decision; do not treat a healthy stack
or merged maintenance PR as phase acceptance.
