## 1. What is being accepted

The **2.0.x stabilization milestone** as scoped by the closeout plan: the C1
starvation reporting, the four C2 maintenance repairs, the C3 tracker and
documentation reconciliation, the C4 audit and the C5 release, deployment and
observation, ending with the final stabilization patch **v2.0.11** and its
eight-hour observation. The old Phase 8 and the 2.0.0 release remain closed
historical milestones and are not reopened.

Patches published or deployed after 2.0.11 (2.0.12, 2.0.13 and three untagged
`main` SHA images) are **2.0 maintenance-line work**. The plan says closing the
milestone does not prohibit later fixes on that line. Each has its own review,
CI and deployment receipt in the roadmap. They are listed in section 3 so their
open limitations are visible at the decision; accepting the close does not
retroactively make them part of the 2.0.11 observation.

## 5. Decisions for the operator

**D1. Accept the close.** Accept the 2.0.x stabilization milestone as closed on
the v2.0.11 evidence, with limitations L1–L24 owned as listed. Recommended.
Accepting it, together with D5, lets N0 open 2.1 (see the [entry record](2.1-entry-n0.md)).

**D2. Release identity of the running code.** Requirement 3 was met for v2.0.11.
Production now runs an untagged image whose labels say 2.0.13.

- **Close now, record L21 (recommended).** The close rests on the 2.0.11
  evidence; the maintenance-line deployments each carry their own receipt; N2
  owns runtime identity. A later 2.0.14 tag remains available on the 2.0
  maintenance line.
- **Tag 2.0.14 first.** Add a version-bump and changelog commit on top of the
  deployed code (`c9c6404` itself reports 2.0.13 in `pyproject.toml` and
  `src/wobblebot/__init__.py`), tag it 2.0.14 and redeploy that tag image before
  closing, so the running version and its label agree. The tag image is a new
  revision, not the one deployed now. This needs separate release and deployment
  authorization. PRs #158 and #162 already carry independent review receipts;
  whether the pre-deploy rule needs anything further for a version-only delta is
  decided at that release.

**D3. Re-check before signing (optional).** The latest read-back is 2026-10-01.
If the operator wants the close receipt to carry a same-day read-back of health,
reconciliation and command state, that is a read-only NAS check run before the
receipt is written.

**D5. Standards exception E02 before N0.** (D4, the 2.1 scope, is in the entry record.) The audit packet's E02 trigger is
"reaffirm or redesign before N0": keep `STATUS.md` as a pointer to the roadmap
(the project rule), or redesign the root ledger. Recommended: reaffirm, since the
project's documentation rule makes the roadmap the sole ledger.

- Accepted limitations (L1–L24, or the amended list) and the D2 choice.
- Verified issue states at that date (on 2026-10-03: #18, #22 and #97 open as
  intentional records; #23 closed; no open pull requests).

Then `STATUS.md`'s pointer text, the backlog's C5 row and the closeout plan's
header point at that receipt.
