## C5 handoff and rollback decisions

Before publishing: accept applicable exceptions, freeze the exact source commit,
prepare patch changelog/version/upgrade notes, run required checks on that version,
and authorize source publication. Verify remote-tip CI, then the tag's own test
and image jobs, published Release and deployment image digest. Recheck 2.0.8
availability; no historical tag is moved.

Before deployment approval: capture the current **file-stack** document and version,
prepare its exact image/Compose diff, retain the prior image digest, and take a
consistent verified backup. Rehearse the tagged prior image against a disposable
migrated database, including inserts and upserts. Local AST-extracted method tests
are supporting evidence, not a substitute for this container rehearsal.

| Failure | Required response |
| --- | --- |
| Candidate cannot read/migrate fixture or breaks an approval/safety invariant | Stop release/deployment; repair and reverify. |
| Migration fails before new financial activity | Stop affected service; use only the verified pre-change recovery path after checking backup integrity. |
| Candidate fails after trades, approvals or transfers occur | Preserve current data. Reconcile post-backup effects before deciding repair/restore. Never overwrite those effects with an old backup. |
| UI/status or delivery regression with compatible database | Consider the rehearsed prior-image path; verify old writes do not refresh stale diagnostic fields on re-upgrade. |
| Loss-capped live service, Harvester failure or ambiguous transfer | Page the operator. No automatic restart or execution retry. |

The proposed acceptance window is eight hours with an explicitly authorized,
finite 15-minute monitor, quiet while unchanged. Record missing natural recovery
events as a specific production-evidence limitation for operator acceptance.
Do not inject production faults or extend observation indefinitely. The
[2.0 limitations](../release/v2.0-known-limitations.md) and every unaccepted
exception must accompany the eventual formal-close decision. N0 starts only
after that decision; N1 is the proposed first implementation slice.
