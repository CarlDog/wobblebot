**Status: draft. Takes effect only after the operator accepts the 2.0.x close**
([acceptance record](2.0-close-acceptance-record.md), decision D1). Prepared
2026-10-03 UTC from `main` `9a42a79`. This is the N0 step of the
[closeout plan](2.0-closeout-and-2.1-entry-plan.md#2-recommended-sequence-and-completion-rule):
reconcile the 2.1 scope, name ADR prerequisites, and select the first slice with
its acceptance criteria. It starts no implementation. The [roadmap](roadmap.md)
records 2.1 as opened once the close is accepted.

## 1. Phase goal and boundary

**2.1: deployment and lifecycle integrity.** Make deployment authority, command
execution, notification delivery and runtime identity explicit and testable,
preserving ADR-001/002/003/004/026/034/041 and the existing safety-cap and restart
semantics (plan §5). Strategy changes, new asset classes and the gated catalog
(G1–G10) are outside 2.1. Phase 9 starts only after 2.1 closes, not when a 2.1
branch or first PR exists.

## 4. First slice: N1 remaining deployment isolation

### Why N1 first

It is the plan's default order. Limitation L6 is the largest residual of
ADR-041: every daemon shares a read-write `/app/data`, and `web`, the most
network-exposed service, holds three billable cloud-LLM keys only to draw a badge
(ADR-041, "Accepted residual"). N2's identity work depends on knowing N1's final
deployment layout.

### Documented acceptance criteria

These are the slice's criteria as already written in the plan §5, ADR-041 and the
backlog's N1 row. N1 is done when all of them hold.

1. **Contract test.** A synthetic capability contract and an isolated Compose
   rehearsal prove every legitimate consumer still works and extra grants fail
   (plan §5).
2. **Legitimate paths keep working.** Legitimate readers and writers, WAL,
   backups and settings paths work under the isolated Compose (backlog N1).
3. **Denied capabilities fail.** A service given a mount or credential beyond its
   row fails the contract test, as ADR-041's credential allowlist already does
   (backlog N1).
4. **Web sheds the cloud keys.** `web` no longer holds the Anthropic, OpenAI or
   Google keys. Its provider-health card is sourced from an authorized daemon
   that already holds them, with explicit freshness and unknown states (plan §5,
   ADR-041).
5. **Decision recorded.** An ADR-041 amendment or new decision records the
   changed data and health ownership (plan §5).
6. **Gates.** Its own design, review, local checks, isolated integration, and
   explicitly authorized live acceptance where needed (plan §5). Per CLAUDE.md,
   the adversarial pre-deploy review and mutation verification gate any code
   deployment of N1.

### Inferred checks

These follow from the criteria and the code but are not written in any plan.
They are proposed for the N1 design to accept, amend or drop.

- **I1. Each grant comes from the code.** As in ADR-041, the consumer list is
  derived from the code that opens each database or file, not from compose
  comments or the example config.
- **I2. Failure is loud and named.** A daemon denied a path it needs exits with a
  named path, the way a missing credential exits 2 with a named variable. It does
  not degrade silently.
- **I3. Rollback.** The isolated layout can be rolled back to the shared mount
  without moving or rewriting a database, so a deployment rollback stays
  image-and-stack-file only.
- **I4. Health honesty.** When the source daemon is down or stale, the web card
  shows unknown or stale. It never shows the last good badge as current.
- **I5. Existing guards stay green.** `tests/deployment/test_compose_capability_matrix.py`
  and `tests/test_architecture_boundaries.py` pass unchanged or are tightened.
  They are never loosened.

### Starting inventory (inferred, to verify in design)

Database consumers as configured in `config/settings.example.yml`. The example
also lists `wobblebot-shadow.db` as a maintenance target; the operator removed it
from the NAS config on 2026-09-19 because that file does not exist there, so it
is left out below. This is
configuration, not proof of which code opens what with which mode. I1 requires
the design to confirm each cell from the source.

| Database | Configured in sections |
| --- | --- |
| `live.db` | live (own), operator, web, maintenance (backup, reconcile source) |
| `operator.db` | live, observe, news, harvest, operator, web, maintenance |
| `observe.db` | observe (own), screener, advise, operator, web, maintenance (prune source) |
| `news.db` | news (own), advise, operator, web, maintenance |
| `advise.db` | advise (own), operator, web, maintenance |
| `harvest.db` | harvest (own), operator, web, maintenance |

Design questions this raises:

- **`operator.db` has seven configured consumers**, several of them writers
  (heartbeats, commands, notifications). Per-service isolation may scope the
  other five databases cleanly while `operator.db` stays shared. If so, the ADR
  should say that plainly rather than call the slice complete.
- **WAL needs a writable directory.** `sqlite_storage.py` sets
  `PRAGMA journal_mode = WAL` on every writable on-disk open, and maintenance runs
  `wal_checkpoint(TRUNCATE)`. Writers create `-wal` and `-shm` files beside each
  database, so per-file bind mounts do not work for writers. `mode=ro` readers of a
  WAL database (`daemon_health.py`, `llm_call_streak.py`) still need the `-shm`
  file, so a read-only directory mount can break them. The design must test each
  reader shape, not assume a read-only mount is safe.
- **Maintenance reads every database** for backups and integrity checks, and writes
  backups and logs. It is likely to remain the broadest data grant.
- **Logs share the data mount** today (`/app/data/logs`). Per-service log paths
  are in scope.
- **Which daemon sources provider health.** `advise` and `operator` both hold the
  cloud keys (ADR-041 matrix). The choice affects freshness when that daemon is
  down and what N4 later observes.

### Out of scope for N1

From ADR-041's alternatives: Docker secret files (`*_FILE` inputs) come after
separation exists; a signing proxy is declined; egress restriction is sequenced
after both. Also out: any change to trading, withdrawal or approval semantics,
which Compose cannot prove (ADR-041, "What this does and does not prove").

### Proposed N1 work order

1. Design note and draft ADR: consumer inventory from source, per-service
   mount plan, journal handling, provider-health source and its freshness
   contract, rollback path.
2. Provider-health source and web change, with tests for fresh, stale, unknown
   and down.
3. Compose per-service mounts and the extended contract test (allowlist for
   mounts as well as credentials).
4. Isolated Compose rehearsal with synthetic data covering all eight daemons,
   backups and settings writes through `tools`.
5. Review, mutation checks and the full gate. A deployment, if any, is a
   separate authorized step on the file-based stack.
