diagnostics, schema migration/readback, the live writer and a web explanation DTO;

Acceptance must cover:

- A zero-order starved grid exposes placed/target counts, refusals, cost-basis
  deferrals, retry cadence and the complete reason breakdown in the rendered card.
  A healthy grid, a partial layout and a stale snapshot must not acquire an
  unsupported claim. Non-cap reasons such as balance shortage or exchange failure
  must not be described as a configurable safety cap.
- PAUSED and OFFSIDE take precedence over STARVED. The engine writer and the web
  builder both prevent frozen starvation state from being presented as current.
  Exercise starved-to-paused, starved-to-offside, recovery and process restart.
- A tick count is never rendered as elapsed starvation time. No invented
  `starved_since` date; persistence does not turn a process-local counter into an
  episode age. Retry text uses the engine's actual policy and remains honest when
  configured tick cadence or processing duration changes.
- Old 2.0.7 data opens safely, migrations are repeatable, malformed diagnostics
  produce defined fallback/error behavior, and unchanged fields survive round trips.
  Rehearse backup/restore and compatibility with the prior image before deployment.
  Compatibility includes old-writer inserts and existing-row upserts followed by a
  new-reader read, including downgrade/re-upgrade or mixed-version intervals. An
  old writer refreshing `updated_at` must not make retained starvation fields fresh.
- Deterministic exchange fixtures show unchanged placements, cancellations, caps,
  sell guards, retry decisions and approval behavior. Diagnostics must not change
  money behavior. Verify the complete engine-to-SQLite-to-web-to-template path.

## 8. Finite execution and exception handling

Each implementation batch ends in verified completion or a named blocker with its
smallest required decision. Begin commands and external operations with the repo's
10-minute checkpoint unless a shorter bound is appropriate; extend once only when
output proves progress. Retry a transient failure once; two materially different
failed recoveries without progress end investigation until the user redirects it.
The explicitly proposed observation window is separate from command timeouts.

An accepted exception records: item ID, precise unmet criterion, evidence, impact,
reason for accepting, operator decision/date, owner, next trigger and whether it
permits source closure, release, deployment or phase entry. Silence and elapsed
time are never acceptance. A data gate becoming eligible never schedules its work
automatically. New audit findings get the same disposition before C5; material
scope growth requires a revised proposal rather than recursive cleanup.

## 10. Author's critical review

This is a **self-review of the proposal**, not the independent review required by
C0/C4 and not a phase-end audit result. It challenged these failure modes:

| Challenge | Resolution in this proposal |
| --- | --- |
| "Address all" quietly becomes build every parked feature. | Finite C0-C5 closeout; every gated category has an owner/trigger and needs disposition, not implementation. |
| The old 2.1 plan reships work or loses its residual risk. | H1/H2 separate shipped controls from N1's shared data mounts and web credentials. |
| The old malformed-row remedy still crashes. | C2.2 requires actual decoder error translation and caller verification; moving the comprehension alone is rejected. |
| A test proves the helper but not the production task list or template. | C1 demands a rendered end-to-end path; C2.1 covers actual composition and task-role reassignment. |
| A calendar date or daily reconciliation summary falsely clears a gate. | G1 checks historical coverage; G3 checks canonical scoring; G5 names the full six-symbol trade-and-ledger tool. |
| A clean boot becomes proof of recovery, or lack of an outage prevents closure forever. | Bounded window, controlled isolated evidence and a separate explicit production-evidence limitation. |
| Health automation restarts the money paths, or rollback erases later financial state. | Page-only exclusions and a pre-agreed, reconciliation-aware rollback procedure. |
| Closing issues or adopting tooling becomes implicit in approving prose. | Per-item evidence and explicit execution/status/deployment decisions; retain the existing package/lint workflow unless its change is approved. |
| Another ledger or archive move creates new drift. | Roadmap owns completion; backlog owns accepted dispositions; historical files keep pointers and provenance. |

Before implementation, an independent plan review must challenge scope completeness,
dependency order, financial/approval boundaries, migration/rollback and test honesty
against the actual candidate. Confirmed findings amend this document before C1.
