## What changes

2.0.8 adds the complete starvation explanation to status cards, preserves truthful
pause/offside/stale behavior, contains unreadable command rows and Discord refusal
transport errors, and makes fatal operator-loop logging match supervision. Missing
Discord/reader credentials stop the relevant CLI with the documented code before
unnecessary work. HTTP healthchecks release error responses before returning
unhealthy. Package manifest, installed metadata and imported version agree.
No runtime dependency, trading-policy, setting or withdrawal-authority change is
part of the patch. The [changelog](../../CHANGELOG.md) carries the release text.

## Storage compatibility contract

The only new persisted columns are in `engine_state`, the operator visibility
side channel. Startup idempotently adds `starved_ticks`, `starved_target`,
`starved_refusals`, `starved_sells_deferred`, `starved_reasons`, and
`starved_updated_at`. These new columns are diagnostic-only. The existing table
also preserves operator pauses that `cli/live` restores after restart, so losing
an old row can resume a deliberately paused symbol. Preserve those existing fields
exactly. Old rows remain readable without a fabricated starvation episode or
elapsed duration.

The freshness marker matters during mixed versions or rollback: a 2.0.7 writer
updates only the columns it understands, including `updated_at`. It cannot clear
or refresh retained starvation fields. On re-upgrade, 2.0.8 suppresses diagnostics
whose freshness no longer matches. Pause/offside precedence and other old fields
remain intact. Fresh 2.0.8 writes can restore a current explanation.

An unreadable pending-command row blocks its requested batch and produces a
sanitized `StorageError`; it is neither skipped nor quarantined. The operator
must inspect and repair the persisted row before dispatch resumes. A healthy
trading process alone does not prove command delivery. Schema migration must
preserve approved rows and must not dispatch them.

## Required isolated image rehearsal

Use the actual published 2.0.7 image and the local candidate built from an exact
tracked source snapshot. Pin the selected prior image by digest. Run with
`--network none`, no credentials, no production mounts and no daemon entry point;
SQLite writes stay in disposable fixtures; container writable layers are ephemeral.
Use each image's installed wheel,
not a host-mounted source package. Capture Python, distribution version, imported
package path, image identity and independent assertion results.

1. Prior image: initialize its real schema and write engine state. Seed valid
   approved-command and notification sentinels plus order/trade/transfer fixtures
   and a fee-bearing non-trade `ledger_entries` row.
   Save a consistent SQLite online backup and logical snapshots of retained rows.
2. Candidate: open the prior fixture, assert integrity, preserved rows and approval
   state, default diagnostics, then write known starvation fields. Reconnect to
   prove repeat migration is stable.
3. Prior image: read the migrated fixture, update an existing engine row and insert
   another. Preserve all unrelated sentinels. Reopen with the prior image again
   to ensure the deployed prior adapter's startup works against the new schema.
4. Candidate: re-upgrade and verify retained raw diagnostics are suppressed after
   old writes; a fresh candidate write restores them. Assert all unrelated rows
   remain byte-for-byte equal as logical SQL values and approvals remain approved.
5. Restore the pre-upgrade backup to a separate disposable database. The prior
   image reads it with no new columns; the candidate can upgrade that restored
   fixture again. Before and after that migration, compare the restored approvals,
   notifications, financial sentinels and old engine state with the saved
   pre-upgrade logical snapshot. Check `PRAGMA integrity_check` after each
   migration/write stage.

The existing unit tests using tagged schema/methods complement this rehearsal.
They do not replace it. Linux tests should import the installed candidate wheel
and preserve mandatory access to the v1.0.0/v2.0.7 tags. Identify every skipped
operator-file check explicitly when real operator settings are absent.

C5-R1's ordinary failed-open shutdown path is repaired and deployed in 2.0.9;
see the [repair evidence](c5-r1-local-repair-evidence.json) and
[roadmap receipt](../planning/roadmap.md). Published `v2.0.8` still contains the
earlier source. Select the verified 2.0.9 artifact identified in the roadmap for
the repair; do not infer that an older artifact contains it.
The [publication evidence](2.0.8-publication-evidence.json) retains both original
tag attempts; a successful retry did not repair the behavior.

Stack 158 is file-managed. Before deployment approval, capture its current full
Compose document, `StackFileVersion`, effective image and prior digest. Prepare
the exact image/Compose diff, preserving unrelated settings. Do not use a git-stack
redeploy or infer applied state from a source push.

Take verified consistent backups of every affected database using the established
online-backup/maintenance path. A raw copy of a live SQLite main file without its
WAL is not a sufficient backup. Record the backup time and which effects occur
after it. Revalidate live configuration and required key scopes without exposing
credentials. Preflight precedes any authorized live session.

After authorized deployment, independently verify persisted stack version/file,
container revision/version/digest, restart policies, health, migrations and
representative operator-facing behavior. No diagnostic trade, transfer, settings
change or production fault injection is implied by this check.

| Trigger | Required action |
| --- | --- |
| Integrity/migration failure, approval regression or misleading safety claim | Stop acceptance and investigate. Do not start another phase. |
| Verified compatible schema but broken candidate behavior | Consider the rehearsed prior-image rollback, preserving current data and verifying freshness suppression on re-upgrade. |
| Need to restore a pre-upgrade database | First reconcile all trades, approvals and transfer effects since the backup. Never overwrite them blindly. The disposable restore test does not authorize a production restore. |
| Loss-capped trader or ambiguous transfer | Page the operator; do not automatically restart or retry the money path. |
| No natural task-failure/recovery event in the acceptance window | Record the evidence limitation for explicit acceptance; do not fabricate an event or wait indefinitely. |

The proposed acceptance is eight hours at 15-minute scheduled checkpoints,
quiet on unchanged state and stopping on completion, failure or required action.
Scheduling requires its own deployment/observation authorization. Formal 2.0.x
closure and N0/N1 entry require the recorded acceptance decision and the
[remaining limitations](v2.0-known-limitations.md).
